# YOLO на RK3588S: полный путь от `.pt` до детекции на NPU

Гайд по развёртыванию `best_5s` на Rockchip RK3588S через RKNPU2.
Версия тулчейна — **rknn-toolkit2 2.3.2** (всё ниже привязано к ней).

**Статус проверки каждого утверждения** помечен так:
`[H]` — проверено локально на этом хосте (тулкит установлен, вызывал сам);
`[D]` — сверено с официальным *RKNN SDK User Guide V2.3.2* и репозиторием
`airockchip/rknn-toolkit2` (пути/имена файлов запрошены через GitHub API);
`[!]` — **не проверено**: платы в песочнице разработки нет. Шаги на плате
написаны по официальной документации, но живьём не прогонялись.

---

## Быстрый путь: модель уже обучена и сконвертирована

Если нужно просто «положить модель на чип» — конвертация уже сделана,
`best_5s_rknn_rk3588_i8.rknn` (10 МБ) лежит в корне репозитория. Разделы 1–3
(экспорт, калибровка, точность) можно пропустить: они про то, как этот файл
получен и как его при желании улучшить.

Остаётся четыре шага, все на плате:

```bash
# 1. драйвер на месте?  (подробности — §4.1)
cat /proc/debug/rknpu/driver_version

# 2. рантайм: положить librknnrt.so 2.3.2+ в /usr/lib  (§4.2)
strings /usr/lib/librknnrt.so | grep -i "librknnrt version"

# 3. Python-обёртка под версию питона платы  (§4.3)
pip install rknn_toolkit_lite2-2.3.2-cp312-...-aarch64.whl

# 4. скопировать на плату и запустить  (§5)
#    best_5s_rknn_rk3588_i8.rknn + rknn_detector_board.py
python rknn_detector_board.py --model best_5s_rknn_rk3588_i8.rknn --cam-index 0
```

Единственное, что реально блокирует: версия `librknnrt.so` на плате должна
быть **не ниже** версии тулкита, которым собрана модель (2.3.2) — см. §4.2.
Это причина большинства «модель не грузится».

## 0. Что вообще происходит

Три звена, и путать их — главный источник боли:

| звено | где исполняется | что делает |
|---|---|---|
| **rknn-toolkit2** | x86_64 Linux хост | `.onnx` → `.rknn`, квантование, симулятор |
| **RKNN Runtime** (`librknnrt.so`) | плата | исполняет `.rknn` на NPU |
| **rknn-toolkit-lite2** (`rknnlite`) | плата | тонкая Python-обёртка над Runtime |

Тулкит на плате **не нужен** и туда не ставится (это x86-пакет). На плате
живут только `librknnrt.so` + `rknnlite`.

### Важно про сам граф

Экспорт (`export_rknn_onnx.py`) даёт **не** тот граф, что `best_5s.onnx`:
9 выходов (3 уровня × `box_raw` / `cls_sigmoid` / `cls_sum`), **без DFL и
декода внутри графа**. Декод считается на CPU.

Это не костыль, а рекомендованный приём: официальный гайд прямо пишет, что
если чувствительный к квантованию слой стоит последним, его исполнение стоит
вынести в постпроцессинг — так его ошибка квантования просто не возникает
`[D]`. DFL-softmax по 16 бинам как раз такой слой.

Практическое следствие: **декод на хосте и на плате обязан быть одинаковым**.
`rknn_detector_board.py::_decode()` — побитовая копия `eval_rknn_accuracy.py::decode()`
(сверено на случайных тензорах: `max|diff| = 0.0`, boxes и scores идентичны) `[H]`.
Меняете один — меняйте второй, иначе симулятор на хосте перестанет предсказывать
поведение платы.

## 1. Хост: окружение

Отдельный venv, **не** смешивать с runtime-окружением `yolo_detector.py`.
Причины пинов — в шапке `requirements-rknn.txt`; коротко: Python ≤3.12
(нет cp313-колеса), `onnx==1.16.1` (тулкит зовёт `onnx.mapping`, удалённый
позже), `numpy<=1.26.4`, torch с CPU-индекса.

```bash
uv python install 3.12
uv venv --python 3.12 /root/rknn_env
uv pip install --python /root/rknn_env/bin/python \
    --index-url https://download.pytorch.org/whl/cpu torch==2.4.0
uv pip install --python /root/rknn_env/bin/python -r requirements-rknn.txt
```

Проверка: `python -c "from rknn.api import RKNN; print('ok')"` `[H]`.

## 2. Хост: конвертация

```bash
python export_rknn_onnx.py --weights /root/best_5s.pt   # -> best_5s_rknn.onnx
python verify_rknn_onnx.py                              # сверка с best_5s.onnx
python build_calib.py --n 100 --seed 0                  # -> calib/*.npy + dataset.txt
python convert_rknn.py --platform rk3588s --dtype i8    # -> *_rk3588_i8.rknn
```

### `rk3588s` → `rk3588`

Валидные `target_platform` в 2.3.2: `rv1103 / rv1103b / rv1106 / rv1106b /
rv1126b / rk3562 / rk3566 / rk3568 / rk3576 / rk3588` — **`rk3588s` в списке
нет** `[H]`. RK3588S это тот же кристалл с урезанной периферией: тот же
3-ядерный NPU, тот же набор инструкций. `convert_rknn.py` сам приводит
`rk3588s` → `rk3588` через `PLATFORM_ALIASES`, так что писать можно любой.

### Про размер калибровочного набора

Официальная рекомендация — **20–200 изображений**, и там же прямо сказано,
что увеличение набора удлиняет квантование, но **не обязательно повышает
точность** `[D]`.

Текущий `dataset.txt` в репозитории — **300** изображений, то есть выше
рекомендованного коридора. Это не ошибка, но и не бесплатно: именно раздутый
набор сделал прогон MMSE неподъёмным по памяти (см. §6). Для новых
экспериментов берите `--n 100`.

Калибровка идёт **тем же letterbox'ом**, что и инференс (сохранение
пропорций + серые поля 114, RGB, NCHW `.npy`), а не resize'ом, который сделал
бы загрузчик RKNN по умолчанию. Иначе диапазоны квантования меряются на одном
распределении, а продакшн видит другое. Подробности и грабли с относительными
путями в `dataset.txt` — в докстринге `build_calib.py`.

## 3. Лестница точности

Официальный порядок действий при нехватке точности `[D]`, снизу вверх:

| уровень | как включить | цена |
|---|---|---|
| **FP16 (без квантования)** | `--dtype fp` | самый точный; ~вдвое медленнее INT8 |
| INT8, `channel` | уже включено | базовый |
| INT8 + `kl_divergence` | `--algorithm kl_divergence` | чуть медленнее сборка |
| INT8 + `mmse` | `--algorithm mmse` | **сборка сильно дольше и прожорливее по RAM** |
| INT8 + hybrid | `--hybrid`, либо `hybrid_quantization_step1/2` | часть слоёв во float → медленнее инференс |
| QAT | переобучение | самый дорогой путь |

Официальные формулировки, чтобы не гадать: `channel` обычно заметно точнее
`layer` (у нас уже `channel`); `mmse` в большинстве сценариев точнее `normal`
и `kl_divergence`, но «работает медленнее и потребляет больше памяти»; на
скорость инференса выбор алгоритма **не** влияет — он влияет только на время
сборки `[D]`.

**Если точность важнее FPS — начинайте с `--dtype fp`.** FP16-модель это
«non-quantized RKNN model which runs with 16-bit half-float data» `[D]`:
калибровка не нужна вообще, расхождение с FP32 — только на уровне округления
fp16. Это верхняя планка, и сравнивать INT8 надо именно с ней.

### Что уже измерено

INT8/`normal`, 300 калибровочных, 60 кадров, порог 0.25, симулятор `[H]`:

| метрика | значение |
|---|---|
| потеряно детекций FP32 | 1 / 53 |
| добавлено детекций | 2 |
| IoU топ-бокса | mean 0.9602, worst 0.7752 |
| кадров с IoU < 0.5 | **0 / 52** |

Локализация не деградировала; единственная потеря — кадр, где FP32 сам был на
грани (0.330 → 0.196).

**Но:** это расхождение INT8↔FP32, а **не** качество детекции. Оно меряет
верность квантования, а не то, видит ли модель вашу цель. Качество на реальной
цели не проверялось ни разу — ни для YOLO, ни для классического детектора.

### Поиск виноватого слоя

Когда точности не хватает, не гадайте — есть `accuracy_analysis()`
(сигнатура `(inputs, output_dir='./snapshot', target=None, device_id=None)`) `[H]`.
Он даёт послойное сравнение с FP32. Дальше по официальной методике: находите
слои с наибольшей просадкой (учитывая, что **ошибка накапливается, поэтому
ранние слои важнее**), вписываете их имена в конфиг гибридного квантования и
пересобираете `[D]`.

## 4. Плата: рантайм

### 4.1 Драйвер

```bash
dmesg | grep -i rknpu
cat /proc/debug/rknpu/driver_version      # -> RKNPU driver: vX.X.X
```

Рекомендуется **>= 0.9.2** `[D]`. Если команды ничего не выводят — в прошивке
нет RKNPU-драйвера (частая беда сторонних сборок); нужен вендорный kernel с
включённым `RKNPU` в kernel config `[D]`.

### 4.2 `librknnrt.so`

Берётся из репозитория `airockchip/rknn-toolkit2`, путь проверен `[D]`:

```
rknpu2/runtime/Linux/librknn_api/aarch64/librknnrt.so   ->   /usr/lib/
```

Проверка версии на плате `[D]`:

```bash
strings /usr/lib/librknnrt.so | grep -i "librknnrt version"
# librknnrt version: X.X.X
```

**Правило совместимости:** для моделей версии 1.5.2 и новее Runtime должен
быть **>= версии модели** `[D]`. Наша модель собрана тулкитом 2.3.2 → на плате
нужен `librknnrt.so` **2.3.2 или новее**. Рассинхрон здесь — источник
«модель не грузится» без внятной диагностики, проверяйте это первым.

### 4.3 `rknnlite`

Колёса лежат в `rknn-toolkit-lite2/packages/`, версия 2.3.2, есть
cp37–cp312 `[D]`:

```bash
pip install rknn_toolkit_lite2-2.3.2-cp312-cp312-manylinux_2_17_aarch64.manylinux2014_aarch64.whl
```

Берите колесо под Python платы и **той же версии, что тулкит на хосте**.

## 5. Плата: запуск

`rknn_detector_board.py` — drop-in замена `YoloDetector` с тем же контрактом
`(x, y, w, h) | None`, поэтому `PAK_OUK_Controller`
(`compute_servo_error` / `check_proximity` / `compute_course_correction`)
подключается без единого изменения — та же линия, что и в основном README.

```bash
python rknn_detector_board.py --model best_5s_rknn_rk3588_i8.rknn --cam-index 0
```

API, сверенный с официальным примером `rknn-toolkit-lite2/examples/resnet18` `[D]`:

```python
from rknnlite.api import RKNNLite
rknn = RKNNLite()
rknn.load_rknn(path)
rknn.init_runtime(core_mask=RKNNLite.NPU_CORE_0_1_2)
outputs = rknn.inference(inputs=[img])
rknn.release()
```

### Препроцессинг: на вход идёт сырой uint8

`mean_values=[[0,0,0]]`, `std_values=[[255,255,255]]` заданы при конвертации,
то есть **нормализацию делает сам NPU**. На плате нельзя делать `/255` и
конвертацию во float — подаётся letterbox-канвас uint8 RGB как есть. Двойная
нормализация здесь — классическая причина «на хосте работает, на плате нет».

### Ядра NPU

Константы: `NPU_CORE_AUTO / _0 / _1 / _2 / _0_1 / _0_1_2 / _ALL`, и они
**действительны только для rk3588 и rk3576** `[H]`.

- минимальная задержка одного кадра → `NPU_CORE_0_1_2`;
- максимальный суммарный FPS → пул из 3 инстансов, по ядру на каждый
  (`NPU_CORE_0`/`_1`/`_2`), либо `NPU_CORE_AUTO`.

Для approach-and-stop важнее задержка, а не throughput: свежесть кадра прямо
влияет на качество управления. Поэтому в `rknn_detector_board.py` по умолчанию
стоит `NPU_CORE_0_1_2`.

### Если пишете на C

`rknn_outputs_get()` по умолчанию отдаёт **квантованные** выходы. Чтобы
получить float32, нужно выставить `outputs[i].want_float = 1` `[D]`. В Python
через `rknnlite` этого делать не надо. Забыть `want_float` в C — ещё одна
типовая причина расхождения с симулятором.

## 6. Измерения и отладка

### FPS

Симулятор точен по арифметике, но **не меряет время** — цифры FPS берутся
только с платы. Варианты:

- на плате: сквозной замер, который печатает `rknn_detector_board.py`;
- с хоста по USB (board-connected): поднять на плате `rknn_server`
  (`rknpu2/runtime/Linux/rknn_server/aarch64/usr/bin/` — там `rknn_server`,
  `start_rknn.sh`, `restart_rknn.sh` `[D]`), затем с хоста
  `init_runtime(target='rk3588')` и `eval_perf()` (сигнатура
  `(is_print=True, fix_freq=True)`) `[H]`. Есть и `eval_memory()`.

Board-connected режим полезен ещё и для разбора расхождений: официальная
методика советует сначала проверить именно им, баг ли это рантайма платы,
и только потом копать свой C-код и пре/постпроцессинг `[D]`.

### Ограничение этого хоста

Машина разработки — **3 ГБ RAM, 2 ядра, без swap**. Сборка с `--algorithm mmse`
на 300 калибровочных изображениях **уронила хост по OOM** (лог обрывается
ровно на `Quantizating: 0%`). Официальная документация подтверждает механику:
MMSE «consumes more memory» `[D]`.

Отсюда практический вывод: MMSE не запрещён, он был просто неправильно
отмасштабирован. `--n 100` (внутри рекомендованного коридора 20–200) —
разумная следующая попытка; следите за `free -g` во время сборки.

`eval_rknn_accuracy.py --json` сохраняет пофреймовые записи, а `--from-json`
переотчитывает их **без повторной сборки квантованного графа** — пользуйтесь
этим вместо перезапуска многоминутной сборки ради переформатирования отчёта.

## 7. Типовые грабли

| симптом | причина |
|---|---|
| модель не грузится на плате | `librknnrt.so` старше версии модели (§4.2) |
| драйвер не находится | прошивка без RKNPU-драйвера (§4.1) |
| `init_runtime` падает | нет `librknnrt.so` в `/usr/lib`, либо нет прав на устройство NPU |
| боксы «уехали» | декод платы разошёлся с `eval_rknn_accuracy.py` (§0) |
| скоры близки к нулю | двойная нормализация: `/255` на CPU поверх std=255 в модели (§5) |
| C-версия расходится с симулятором | не выставлен `want_float = 1` (§5) |
| `core_mask` не действует | платформа не rk3588/rk3576 (§5) |
| `AttributeError: onnx has no attribute 'mapping'` | onnx новее 1.16.1 (§1) |
| хост умирает при сборке | MMSE/hybrid на большом калибровочном наборе (§6) |
