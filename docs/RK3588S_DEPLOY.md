# YOLO на RK3588S: от `.pt` до детекции на NPU

Общий гайд: как взять **свою** обученную YOLO-модель и запустить её на
Rockchip RK3588 / RK3588S через RKNPU2. Версия тулчейна —
**rknn-toolkit2 2.3.2**, всё ниже привязано к ней.

Гайд не привязан к конкретным весам. Везде, где встречается `your_model`,
подставляйте свои.

**Статус проверки каждого утверждения:**

| метка | значение |
|---|---|
| `[H]` | проверено локально: тулкит установлен, вызов сделан, вывод прочитан |
| `[D]` | сверено с официальным *RKNN SDK User Guide V2.3.2* и репозиторием `airockchip/rknn-toolkit2` |
| `[!]` | **не проверено** — платы нет, написано по документации |

---

## Маршрут

```
your_model.pt
    │  §2  определить тип головы          ← начните отсюда
    ▼
your_model.onnx  (голова вырезана)
    │  §3  экспорт
    ▼
calib/*.npy + dataset.txt
    │  §4  калибровка
    ▼
your_model_rk3588_i8.rknn
    │  §5  конвертация
    │  §6  проверка, что квантование не сломало точность
    ▼
плата: §7 рантайм → §8 запуск
```

Шаги §7–§8 (board-side) **не зависят от модели вообще** — рантайму всё равно,
что вы в него загрузили. Модель-специфичны только §2, §3 и декод в §8.

## 1. Принцип: голова не едет на NPU

Ключевая идея, общая для всех NPU-стеков: на NPU уходит **backbone**
(свёртки), а **detection head и NMS считаются на CPU**. Эти операции плохо
квантуются и на NPU ложатся плохо.

Официальный гайд Rockchip формулирует это как рекомендацию: если
чувствительный к квантованию слой стоит последним, его исполнение стоит
вынести в постпроцессинг — тогда его ошибка квантования просто не возникает
`[D]`.

Практически: **экспортированный ONNX не должен содержать декод**. У
YOLO-экспорта под NPU выходов не один, а по 2–3 на каждый уровень детекции,
«сырых», до декода.

Отсюда правило, которое ломает больше всего людей:

> Декод, который вы пишете на CPU, обязан **точно** соответствовать тому, что
> вырезали из графа, и быть **одинаковым** на хосте (где вы меряете точность в
> симуляторе) и на плате. Разошлись — симулятор перестал предсказывать
> поведение железа, и вы отлаживаете вслепую.

В этом репозитории декод продублирован в `eval_rknn_accuracy.py::decode()`
(хост) и `rknn_detector_board.py::_decode()` (плата); совпадение проверяется
побитово `[H]`. Меняете один — меняйте второй.

## 2. Определите тип головы своей модели

Первый шаг, и он решает, сколько из гайда вам подходит.

```bash
python -c "
import onnxruntime as ort
s = ort.InferenceSession('your_model.onnx', providers=['CPUExecutionProvider'])
for i in s.get_inputs():  print('IN ', i.name, i.shape)
for o in s.get_outputs(): print('OUT', o.name, o.shape)
"
```

| что видите | что это | что делать |
|---|---|---|
| 1 выход `[1, 4+nc, N]`, без objectness | Ultralytics v8/v11, anchor-free + DFL | весь гайд подходит, §3 сработает как есть |
| выходы по 64 канала (`4 × reg_max 16`) | уже RKNN-экспорт DFL | §3 пропустить, идти в §4 |
| 3 выхода `[1,3,H,W,5+nc]` | YOLOv5/v7, anchor-based | §3 → форк `airockchip/yolov5`, декод другой (§2.1) |
| выход вида `[1,300,6]`, финальные боксы | **YOLO26** или YOLOv10 — end-to-end, NMS-free | декода почти нет, но и §3 не подходит (§2.2) |
| доп. выход `[1,32,160,160]` | сегментация | детекторная часть подойдёт, маски нет |
| не Ultralytics | своя сеть | §1, §4–§7, §9–§10 применимы; §3 и декод — свои |

**Anchor-free vs anchor-based — как отличить наверняка:** anchor-based
(YOLOv5/v7) всегда несёт канал objectness, поэтому последняя размерность
`5+nc`. Anchor-free (v8/v11) objectness не имеет: `4+nc`. Если в экспорте
появились box-тензоры с 64 каналами — это DFL, `4 × reg_max`, и точно
anchor-free.

### 2.1 Если у вас настоящий YOLOv5

Форк Rockchip — `github.com/airockchip/yolov5` (проверено: репозиторий
существует, есть `export.py` и `README_rkopt.md`) `[D]`:

```bash
python export.py --rknpu --weight your_model.pt
```

Из `README_rkopt.md` дословно: *«Change output node, remove post_process from
the model»*, потому что исходный post-process *«unfriendly for quantization»*;
рядом генерируется `RK_anchors.txt` для CPU-постобработки `[D]`. README
отдельно просит вызывать именно с флагом, а не править значение по умолчанию
в `export.py`.

Дальше §4 и далее работают одинаково, но **декод в §8 вам не подойдёт** — он
DFL. Нужен anchor-based декод с якорями из `RK_anchors.txt`.

### 2.2 YOLO26 (в т.ч. yolo26n) — поддержано, но есть две ловушки

Всё ниже проверено локально на ultralytics **8.4.112**, модель собрана из
`yolo26n.yaml` `[H]`:

```
head: nl=3 nc=80 reg_max=1 strides=[8, 16, 32]
      end2end=True -> exporting one2one_cv2/cv3
      DFL=no (reg_max=1, YOLO26-style) -> box branch is 4 ch
```

**Ловушка 1: DFL нет, и старый декод молча врёт.**
В YOLO26 отказ от DFL реализован как `reg_max=1`, из-за чего
`self.dfl = DFL(reg_max) if reg_max > 1 else nn.Identity()` становится
`Identity`, а box-ветка выдаёт **4 канала вместо 64**. Ветка несёт готовые
ltrb-расстояния, softmax-свёртка не нужна.

Опасность в том, что DFL-декод на 4-канальном тензоре **не падает**: `mc`
становится 1, softmax по одному бину даёт 1.0, матожидание против
`arange(1) = [0]` даёт 0 — и **все боксы схлопываются в нулевой размер**.
Измерено на реальном экспорте yolo26n: старый путь давал средние w/h
`0.0000`, новый — `42.67` при 8400/8400 ненулевых боксов `[H]`.

Декод в этом репозитории теперь ветвится по числу каналов автоматически
(`>4` → DFL, `==4` → напрямую), так что и v8/v11, и YOLO26 работают одним
кодом. Хостовый и платный декод на выходах yolo26n совпадают побитово `[H]`.

**Ловушка 2: у YOLO26 две головы, экспортировать надо правильную.**
При `end2end=True` (умолчание) модель несёт две пары веток: `cv2`/`cv3`
(one-to-many, вспомогательная при обучении) и `one2one_cv2`/`one2one_cv3` —
именно её использует forward на инференсе. Формы у них одинаковые
(`box (1,4,·,·)`, `cls (1,nc,·,·)`) `[H]`, поэтому экспорт «не той» пары
отработает без ошибок и даже даст правдоподобные боксы — расхождение вылезет
только как необъяснимо худшая точность против `.pt`.
`export_rknn_onnx.py` выбирает пару по флагу `end2end` сам и печатает, какую
взял.

**Про NMS.** Одноголовый one-to-one выдаёт по одному предсказанию на объект,
поэтому NMS формально не нужен; Ultralytics заявляет ~43% ускорения на CPU
относительно NMS-based базлайнов. В `rknn_detector_board.py` NMS всё равно
вызывается — на one-to-one выходах он практически no-op и стоит копейки,
зато один и тот же код работает для всех голов. Хотите убрать — убирайте
осознанно.

**Готового примера под YOLO26 в `rknn_model_zoo` нет** — там `yolov5 / yolov6
/ yolov7 / yolov8 / yolo11 / yolov10 / yolox / ppyoloe`, последний push
2025-04-09 `[D]`. Референсной реализации не будет, ориентируйтесь на этот
репозиторий.

Разделы §4–§7 и §9–§10 применимы без изменений — они про NPU, а не про голову.

Источники: [Ultralytics YOLO26 Docs](https://docs.ultralytics.com/models/yolo26),
[почему убрали NMS](https://www.ultralytics.com/blog/why-ultralytics-yolo26-removes-nms-and-how-that-changes-deployment),
[end-to-end detection](https://docs.ultralytics.com/guides/end2end-detection).

## 3. Экспорт (Ultralytics: v8 / v11 / YOLO26)  `[H]`

`export_rknn_onnx.py` воспроизводит RKNN-ветку экспорта airockchip против
**локально установленного** ultralytics, а не через форк
`airockchip/ultralytics_yolov8`: форк прибит к ultralytics 8.0.x, и чекпоинт,
обученный на 8.4.x, там не грузится — падает на `state_dict`.

```bash
python export_rknn_onnx.py --weights your_model.pt --imgsz 640 --out your_model.onnx
```

На выходе — 3 тензора на уровень: `box_raw`, `cls_sigmoid`, `cls_sum`.
Работает и для DFL-голов (v8/v11, box 64 канала), и для YOLO26
(`reg_max=1`, box 4 канала) — скрипт сам определяет вариант и сам выбирает
one2one-пару у end2end-моделей (§2.2).

Проверьте шапку, которую он печатает — `nl`, `nc`, `reg_max`, strides,
какая пара веток взята и нужен ли софтмакс в декоде. Это самая дешёвая
проверка, что вы экспортируете то, что думаете:

```
head: nl=3 nc=80 reg_max=1 strides=[8, 16, 32]
      end2end=True -> exporting one2one_cv2/cv3
      DFL=no (reg_max=1, YOLO26-style) -> box branch is 4 ch
```

## 4. Калибровка  `[H]`

```bash
python build_calib.py --imgsz 640 --n 200 --globs "your_data/**/*.jpg"
```

Три вещи, каждая из которых тихо стоит точности:

**Препроцессинг должен совпадать с инференсом.** Загрузчик RKNN по умолчанию
делает простой resize, растягивая картинку. Если на плате вы letterbox'ите
(сохранение пропорций + серые поля), а калибруете растянутыми — диапазоны
квантования измерены не на том распределении, которое увидит продакшн.
`build_calib.py` letterbox'ит.

**Размер набора: 20–200 изображений.** Официальная рекомендация, и там же
сказано, что больше — **не обязательно точнее**, только дольше `[D]`.

**Набор должен быть из вашего домена** и покрывать распределения, которые
модель реально увидит. Кадры без цели полезны, но следите, чтобы на них не
было ложных срабатываний.

Порядок каналов здесь RGB, паддинг 114 (`--pad`). Если ваша сеть обучена на
BGR — меняйте `quant_img_RGB2BGR` в `convert_rknn.py` и `cvtColor`
согласованно.

## 5. Конвертация  `[H]`

```bash
python convert_rknn.py --onnx your_model.onnx --platform rk3588s --dtype i8
```

**`rk3588s` → `rk3588`.** Валидные `target_platform` в 2.3.2: `rv1103 /
rv1103b / rv1106 / rv1106b / rv1126b / rk3562 / rk3566 / rk3568 / rk3576 /
rk3588` — **`rk3588s` в списке нет** `[H]`. RK3588S — тот же кристалл с
урезанной периферией: тот же 3-ядерный NPU, тот же набор инструкций.
`convert_rknn.py` подставляет алиас сам.

`mean_values=[[0,0,0]]`, `std_values=[[255,255,255]]` задаются здесь — то есть
**нормализацию берёт на себя NPU**, и на плату идут сырые uint8-пиксели.

### Лестница точности  `[D]`

| уровень | как включить | цена |
|---|---|---|
| **FP16, без квантования** | `--dtype fp` | самый точный; ~вдвое медленнее INT8 |
| INT8, `channel` | по умолчанию | базовый |
| INT8 + `kl_divergence` | `--algorithm kl_divergence` | сборка чуть дольше |
| INT8 + `mmse` | `--algorithm mmse` | сборка дольше и **прожорливее по RAM** |
| INT8 + hybrid | `--hybrid` | часть слоёв во float → медленнее инференс |
| QAT | переобучение | самый дорогой путь |

Официально: `channel` обычно заметно точнее `layer`; `mmse` в большинстве
сценариев точнее `normal` и `kl_divergence`; на скорость инференса выбор
алгоритма **не влияет**, только на время сборки `[D]`.

Нужна максимальная точность — начинайте с `--dtype fp`: это «non-quantized
RKNN model which runs with 16-bit half-float data» `[D]`, калибровка не нужна
вообще.

## 6. Проверка, что квантование ничего не сломало  `[H]`

```bash
python eval_rknn_accuracy.py --onnx your_model.onnx \
    --rknn your_model_rk3588_i8.rknn --imgsz 640 --json eval.json
```

Гоняет `.rknn` в симуляторе тулкита и сравнивает с FP32 ONNX на одних кадрах.
Симулятор бит-точен по арифметике, но **время не меряет**.

Смотреть надо не на среднюю ошибку, а на:

- **сколько детекций INT8 потерял** относительно FP32 — единственная метрика,
  напрямую отражающая деградацию;
- **число кадров с IoU < 0.5** — реальные регрессии локализации;
- средний сдвиг скора полезен только как ранний признак.

`--from-json` переотчитывает сохранённый прогон **без повторной сборки**
квантованного графа.

Не хватает точности — не гадайте: `accuracy_analysis()` (сигнатура
`(inputs, output_dir='./snapshot', target=None, device_id=None)` `[H]`) даёт
послойное сравнение с FP32. Дальше по официальной методике: находите слои с
наибольшей просадкой (**ошибка накапливается, ранние слои важнее**),
вписываете их в конфиг гибридного квантования, пересобираете `[D]`.

<details>
<summary>Ориентир: какой порядок потерь считать нормальным</summary>

Замер на одноклассовом DFL-детекторе. INT8/`normal`, 300 калибровочных, 60
кадров, порог 0.25, симулятор `[H]`: потеряна 1 детекция из 53, добавлено 2,
IoU топ-бокса mean 0.9602 / worst 0.7752, кадров с IoU < 0.5 — **0 из 52**.
Локализация не пострадала; единственная потеря была на кадре, где FP32 сам
стоял на пороге (0.330 → 0.196).

Это расхождение INT8↔FP32, а **не** качество детекции: метрика говорит, что
квантование верное, а не что модель видит цель.
</details>

## 7. Плата: рантайм  `[ЛЮБАЯ МОДЕЛЬ]`

Здесь и до конца §8 всё **не зависит от того, что у вас за модель**.

| звено | где | что делает |
|---|---|---|
| `rknn-toolkit2` | x86_64 хост | `.onnx` → `.rknn` |
| `librknnrt.so` | плата | исполняет `.rknn` на NPU |
| `rknnlite` | плата | Python-обёртка над Runtime |

Тулкит на плату **не ставится** — это x86-пакет.

### 7.1 Драйвер

```bash
dmesg | grep -i rknpu
cat /proc/debug/rknpu/driver_version      # -> RKNPU driver: vX.X.X
```

Рекомендуется **≥ 0.9.2** `[D]`. Ничего не выводит — в прошивке нет
RKNPU-драйвера (частая беда сторонних сборок), нужен вендорный kernel `[D]`.

### 7.2 librknnrt.so

Путь в репозитории `airockchip/rknn-toolkit2` проверен `[D]`:

```
rknpu2/runtime/Linux/librknn_api/aarch64/librknnrt.so   ->   /usr/lib/
```

```bash
strings /usr/lib/librknnrt.so | grep -i "librknnrt version"
```

> **Правило совместимости.** Для моделей версии 1.5.2 и новее Runtime должен
> быть **≥ версии модели** `[D]`. Собрали тулкитом 2.3.2 → нужен
> `librknnrt.so` 2.3.2+. Рассинхрон здесь — причина большинства «модель не
> грузится» без внятной диагностики. Проверяйте первым.

### 7.3 rknnlite

Колёса в `rknn-toolkit-lite2/packages/`, версия 2.3.2, cp37–cp312 `[D]`:

```bash
pip install rknn_toolkit_lite2-2.3.2-cp312-cp312-manylinux_2_17_aarch64.manylinux2014_aarch64.whl
```

Берите **ту же версию, что тулкит на хосте**.

## 8. Плата: запуск

```bash
python rknn_detector_board.py --model your_model_rk3588_i8.rknn \
    --imgsz 640 --classes 0 2
```

API, сверенный с официальным примером `rknn-toolkit-lite2/examples/resnet18` `[D]`:

```python
from rknnlite.api import RKNNLite
rknn = RKNNLite()
rknn.load_rknn(path)
rknn.init_runtime(core_mask=RKNNLite.NPU_CORE_0_1_2)
outputs = rknn.inference(inputs=[img])
rknn.release()
```

**На вход идёт сырой uint8.** `mean/std` заданы при конвертации, нормализацию
делает NPU. Никакого `/255` и float-приведения на CPU — двойная нормализация
это классическое «на хосте работает, на плате нет».

**Многоклассовая модель:** без `--classes` детектор берёт лучший бокс любого
класса, что верно только при `nc=1`. Передайте id целевых классов:
`--classes 0 2 5`, или в коде `RknnYoloDetector(path, classes=[0,2,5])`.

**Ядра NPU.** Константы `NPU_CORE_AUTO / _0 / _1 / _2 / _0_1 / _0_1_2 / _ALL`
действительны **только для rk3588 и rk3576** `[H]`. Минимальная задержка
кадра → `_0_1_2`; максимальный суммарный FPS → пул из 3 инстансов по ядру.

**Если пишете на C:** `rknn_outputs_get()` по умолчанию отдаёт
**квантованные** выходы; для float32 выставьте `outputs[i].want_float = 1`
`[D]`. В Python через `rknnlite` это не нужно.

Декод обобщён по `nc`, `imgsz`, `reg_max` и числу уровней — всё выводится из
форм тензоров. Совпадение с хостовым декодом проверено на `nc` = 1/3/80,
`imgsz` = 320/640/960, `reg_max` = 8/16, 2 и 3 уровнях — побитово во всех
случаях `[H]`.

## 9. Измерения и отладка  `[ЛЮБАЯ МОДЕЛЬ]`

FPS берётся **только с платы** — симулятор время не меряет.

- на плате: сквозной замер печатает `rknn_detector_board.py`;
- с хоста: поднять на плате `rknn_server`
  (`rknpu2/runtime/Linux/rknn_server/aarch64/usr/bin/` — там `rknn_server`,
  `start_rknn.sh`, `restart_rknn.sh` `[D]`), затем
  `init_runtime(target='rk3588')` и `eval_perf(is_print=True, fix_freq=True)`
  `[H]`. Есть и `eval_memory()`.

Board-connected режим — штатный способ разбирать расхождения: официальная
методика советует сначала проверить им, баг ли это рантайма платы, и только
потом копать свой код `[D]`.

**Про память хоста.** Сборка с `--algorithm mmse` на 300 калибровочных
изображениях уронила по OOM хост с 3 ГБ RAM без swap (лог обрывается ровно на
`Quantizating: 0%`). Документация подтверждает: MMSE «consumes more memory»
`[D]`. Держитесь коридора 20–200 картинок и следите за `free -g`.

## 10. Типовые грабли

| симптом | причина |
|---|---|
| модель не грузится на плате | `librknnrt.so` старше версии модели (§7.2) |
| драйвер не находится | прошивка без RKNPU-драйвера (§7.1) |
| `init_runtime` падает | нет `librknnrt.so` в `/usr/lib` или прав на устройство |
| боксы «уехали» | декод платы разошёлся с хостовым (§1) |
| скоры около нуля | двойная нормализация `/255` поверх std=255 (§8) |
| детектор ловит не тот объект | многоклассовая модель без `--classes` (§8) |
| необъяснимая потеря точности | `--imgsz` при калибровке ≠ при экспорте (§4) |
| C-версия расходится с симулятором | не выставлен `want_float = 1` (§8) |
| `core_mask` не действует | платформа не rk3588/rk3576 (§8) |
| `onnx has no attribute 'mapping'` | onnx новее 1.16.1 |
| хост умирает при сборке | MMSE/hybrid на большом наборе (§9) |

## 12. Что здесь не проверено

- **§7 и §8 не прогонялись на железе** — платы нет. Сверено с официальным
  гайдом V2.3.2 и путями в репозитории, но это документация, а не
  подтверждённый запуск `[!]`.
- `rknn_detector_board.py`: декод сверен с хостовым побитово `[H]`,
  `RKNNLite`-часть на плате не запускалась `[!]`.
- FPS не измерялся нигде — симулятор его не даёт `[H]`.
- FP16-ветка (`--dtype fp`) не собиралась; сравнения INT8↔FP16 нет `[!]`.
- Путь YOLO26 (§2.2): экспорт и декод **прогонялись** — на модели, собранной
  из `yolo26n.yaml` (архитектура настоящая, веса случайные), поэтому формы,
  выбор one2one-пары и ветвление декода по числу каналов проверены `[H]`.
  А вот конвертация YOLO26 в `.rknn` и замер потери INT8 на нём **не
  делались** — цифры §6 получены на DFL-голове `[!]`.

Первое при появлении платы: пройти §7 по шагам, затем сравнить выход
`rknn_detector_board.py` на десятке кадров с `eval_rknn_accuracy.py
--from-json` по тем же файлам. Сходится — пайплайн верен end-to-end.

## Приложение: Allwinner T527 / OrangePi 4A

Другая плата — **другой стек целиком**, ничего из §3–§9 не переносится:

| | RK3588S | Allwinner T527 |
|---|---|---|
| тулчейн | `rknn-toolkit2` | `pegasus_*.sh` в Docker-образе |
| артефакт | `.rknn` | `.nb` (`network_binary.nb`) |
| рантайм | `librknnrt.so` + `rknnlite` | `viplite` + ai-sdk (C) |
| SDK | `airockchip/rknn-toolkit2` | `ZIFENG278/ai-sdk` |

Переносится только **принцип из §1** — вырезать голову, считать её на CPU.
Именно поэтому экспорт `--rknpu` из форка Rockchip работает и для Allwinner:
он всего лишь убирает post-process из графа, а это нужно обоим.

Пошаговая инструкция по этому пути есть у коллеги
(`Claude_Corner/Instruction.odt`). Здесь она сознательно не переписана: она не
проверялась, платы T527 нет, и выдавать чужой непроверенный текст за часть
этого гайда значило бы соврать про статус `[!]`.

Две вещи, замеченные при сверке ссылок из того документа: `ai-sdk` —
репозиторий на 21 звезду с одним мейнтейнером, последний push 2025-10-20, и на
нём держится весь путь; указанный там `yolov5_pre_process.cpp` в текущем HEAD
отсутствует (препроцессинг, судя по всему, ушёл в `main.c`).
